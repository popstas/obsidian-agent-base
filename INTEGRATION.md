# INTEGRATION — адаптация скиллов под пользователя

**Этот документ для агента (любого: Claude Code, Codex, Hermes, OpenClaw, Antigravity и др.), а не для конечного пользователя.**

Скиллы в этом репозитории — обезличенные шаблоны. В них зашиты примеры, дефолты и
условности под абстрактный «рабочий vault». Если просто скопировать их в чужой проект,
пользователь получит чужие доменные папки (`Platform/`, `Companies/`), чужой трекер
(`CRM`) и ссылки на скиллы, которых у него нет.

**Поэтому не останавливайся на том, что скиллы просто оказались в vault. Прогони
адаптацию: спроси пользователя про уровень настройки, задай вопросы из нужной группы,
отредактируй файлы под ответы и покажи диф.**

## Шаг 0 — поставить Obsidian и подключить vault

Первым делом, до вопросов адаптации. Актуально в режимах 1 и 2 (vault лежит на диске).
Если Obsidian уже стоит и папка открыта как vault — пропусти, но убедись, а не
предполагай.

1. **Дай ссылку под ОС пользователя.** ОС видно из окружения агента (`darwin` → macOS,
   `win32` → Windows, `linux` → Linux). Ссылка одна — <https://obsidian.md/download>, —
   но скажи, что именно качать: macOS — `.dmg` (universal, подходит и Apple Silicon, и
   Intel), Windows — `.exe`, Linux — AppImage, `.deb` или Snap/Flatpak на выбор. Если
   ОС определить нельзя, дай страницу без уточнения.
2. **Дождись подтверждения «поставил».** Дальше не иди: следующий шаг делается руками в
   уже запущенном приложении.
3. **Подключи папку как vault.** На первом запуске Obsidian показывает окно выбора —
   там **Open folder as vault**. Если приложение уже открыто: значок vault в левом
   нижнем углу → **Open another vault** → **Open folder as vault**. Путь отдай
   отдельным блоком кода, чтобы копировался одной кнопкой:

   ```
   ~/vaults/work
   ```

   Подставь реальный абсолютный путь к vault на машине пользователя (на Windows —
   вида `D:\vaults\work`). Именно этот шаг регистрирует vault в Obsidian.
4. **Дай deeplink и предложи сохранить в закладки.** Работает только после шага 3:

   ```
   obsidian://open?vault=work
   ```

   Имя vault — имя папки, если пользователь не переименовал его при подключении;
   пробелы кодируй как `%20`. Можно сразу на стартовую заметку:
   `obsidian://open?vault=work&file=index`.

> **Deeplink не подключает vault.** И `obsidian://open?vault=…`, и `?path=…` ищут
> только среди уже зарегистрированных хранилищ — для незнакомой папки Obsidian ответит
> `Vault not found`. Официальной ссылки вида «открыть папку как vault» не существует,
> обойти шаг 3 нельзя. Не предлагай пользователю править `obsidian.json` руками.

## Сначала определи режим

Спроси пользователя (или определи сам по признакам):

1. **Новый vault из клона базы** — в корне есть `demo-manifest.json` и `skills/`. Полная адаптация плюс удаление демо в конце.

   > **Разовая настройка на каждой машине.** Если пользователь ещё не выполнял
   > `/plugin marketplace add .` в этой сессии агента — скиллы vault не активированы,
   > и их не видно даже несмотря на клон. Команда регистрирует marketplace в
   > **пользовательском** `~/.claude/settings.json`, а не в клоне, поэтому шаг
   > повторяется на каждой машине пользователя, а не один раз на vault. Проверь и
   > при необходимости попроси выполнить перед адаптацией.

2. **Существующий vault, скиллы из плагина** — `demo-manifest.json` отсутствует, скиллы приходят из marketplace. Демо удалять нечего; вместо этого нужно свести уже существующую структуру vault с ожидаемой: проверить наличие файлов лестницы, формат дневных логов, каталог вложений.
3. **Только скиллы** — vault нет. Адаптируй лишь те скиллы, которые пользователь собирается применять.

## Чтобы скиллы увидел Codex (и ChatGPT)

Codex ищет скиллы не там, где Claude Code. Он сканирует, в порядке приоритета:
`.agents/skills` в текущем каталоге или корне репозитория, затем `$HOME/.agents/skills`,
`/etc/codex/skills` и встроенные. Скиллы vault лежат в `skills/` (в клоне базы) или в
`.claude/skills` (в некоторых vault), поэтому Codex их не видит, пока не появится
`.agents/skills`, указывающий на этот каталог. Симлинки Codex разворачивает и
подхватывает изменения на лету, так что копировать файлы не нужно — нужна связь.

**Агент делает это сам:** определи ОС и реальный каталог со скиллами, покажи
пользователю точную команду, **спроси подтверждение** и выполни её. Не отдавай
пользователю инструкцию «скопируй и выполни», если можешь выполнить сам.

macOS / Linux:

```bash
mkdir -p .agents && ln -s ../skills .agents/skills
```

Windows (junction — не требует прав администратора и режима разработчика, в отличие от
symlink):

```powershell
New-Item -ItemType Directory -Force .agents
New-Item -ItemType Junction `
  -Path .agents\skills `
  -Target (Resolve-Path .claude\skills)
```

Подставь в `-Target` (и в `ln -s`) тот каталог, где скиллы лежат на самом деле:
`skills` в корне для клона базы, `.claude\skills` — если они там.

**Windows: связь ставится только на локальном томе.** Если vault лежит на
подключённом сетевом или мапленном диске, junction не создаётся —
`New-Item` отвечает `Local NTFS volumes are required to complete the operation`.
Запасной путь через `-ItemType SymbolicLink` тоже не выручит: на Windows он
требует прав администратора (`NewItemSymbolicLinkElevationRequired`). Рабочий
обход один — перенести vault на локальный том и повторить команду там.

Проверка: `ls .agents/skills` (`dir .agents\skills`) показывает папки скиллов; в сессии
Codex они вызываются как `$new-task`, `$worklog` и т.д.

Связь локальная для машины: junction в git не переносится, а симлинк переносится только
между Unix-системами. Добавь `.agents/` в `.gitignore` vault и повтори шаг на каждой
машине — как и `/plugin marketplace add .` для Claude Code.

**ChatGPT в вебе (в том числе Work) — это не покрывает.** Там нет файловой системы:
`.agents/skills` ему недоступен, скиллы грузятся отдельно (`Customize → Skills →
Upload`, по одному zip-архиву с `SKILL.md` внутри; на всю организацию — `Organization
settings → Skills`), а до самих файлов vault ChatGPT дотянется только через
MCP-коннектор или синк каталога в подключённое хранилище. Ссылка `.agents/skills` нужна
для Codex — CLI и расширений IDE.

## Чтобы хуки увидел Codex

Хуки Codex лежат в `<repo>/.codex/hooks.json` и используют ту же схему, что
Claude Code: `SessionStart`, `matcher`, `type: "command"`. В отличие от
`.agents/skills`, это обычный коммитимый файл — он уже в репозитории, создавать
ничего не нужно. Хук один: подсказка на старте сессии заглянуть в `tasks.md`
и в лог текущего дня.

Сверх схемы Claude Code у Codex есть поле `commandWindows` — команда для Windows.
Благодаря ему один и тот же хук работает на трёх ОС без Node: на macOS и Linux
запускается `.codex/hooks/tasks-startup.sh`, на Windows —
`.codex/hooks/tasks-startup.ps1`.

Что нужно сделать один раз:

1. **Включить хуки в `~/.codex/config.toml`. Агент делает это сам:** открой файл,
   проверь, есть ли уже секция `[features]`, покажи пользователю точную правку,
   **спроси подтверждение** и внеси её сам. Не отдавай пользователю инструкцию
   «допиши это в конфиг», если можешь дописать сам.

   - Секции `[features]` ещё нет или файла нет вовсе — добавь:

     ```toml
     [features]
     hooks = true
     ```

   - Секция `[features]` уже есть — допиши строку `hooks = true` в неё, не
     создавая вторую секцию `[features]` в том же файле.

2. При первом запуске Codex спросит, доверять ли файлу хуков. Это интерактивный
   промпт внутри самого бинаря `codex` — его нельзя выполнить за пользователя,
   ответить должен он сам. Это штатное поведение: подтверждённый хеш
   сохраняется в `[hooks.state]` того же `config.toml` и переспрашивается
   только при изменении файла.

Проверка: запусти `codex` в каталоге vault — в начале сессии должна появиться
строка статуса «Loading tasks», а агент сам перечислит задачи из `tasks.md`.
Схема `.codex/hooks.json` ни разу не проверялась в живой сессии Codex — если
ожидаемого не произошло, разбирайся по пунктам, а не сразу считай всё
сломанным:

- **`[features] hooks = true` действительно стоит в `~/.codex/config.toml`**,
  и секция `[features]` там одна (см. предупреждение в шаге 1 выше про вторую
  секцию).
- **Промпт доверия файлу хуков был подтверждён.** Проверь это по
  `[hooks.state]` того же `config.toml` — там должен появиться ключ,
  содержащий путь `.codex/hooks.json` этого vault. Нет такой записи — файл ни
  разу не загружался.
- **Версия `codex` не старше той, что умеет хуки** (0.144.1 на момент
  написания). Более старая может вообще не читать `.codex/hooks.json`.
- **`codex debug prompt-input` хуки не запускает** — это тупиковый путь
  проверки, команда только рендерит контекст, а не выполняет хуки. Проверять
  через неё не нужно, эта ветка уже отняла время у проекта.
- **Отдели «скрипт сломан» от «хук не сработал»**, запустив близнецов
  напрямую: `.codex/hooks/tasks-startup.sh` под bash и
  `.codex/hooks/tasks-startup.ps1` под `powershell.exe -NoProfile -File`. Оба
  должны напечатать в stdout JSON вида `{"hookSpecificOutput": {...}}`. На
  Windows 11 (Windows PowerShell 5.1 + Git Bash, консоль не в UTF-8) это
  подтверждено: оба возвращают код 0, валидный JSON с одинаковым разобранным
  содержимым и кириллицу настоящим UTF-8 в сырых байтах — то есть сами
  скрипты рабочие, а непроверена именно связка схемы `.codex/hooks.json` с
  живым `codex`.
- **Если строка статуса так и не появилась — это не поломка.** Агент и без
  неё читает `tasks.md` и лог текущего дня сам; хук — только удобство, а не
  обязательное условие работы.

**ChatGPT это не покрывает — ни веб, ни десктоп.** Локальные хуки исполняют
только Codex CLI и расширения IDE. У ChatGPT нет процесса, который бы их
запустил, поэтому там работают только скиллы (см. раздел выше). Ничего
настраивать не нужно — и ничего не сломано.

**Хуки Claude Code остаются на Node.** Поля `commandWindows` у Claude Code нет,
поэтому одной строкой команды две ОС там не покрыть. Если Node на машине нет,
`.claude/hooks/*` просто тихо не сработают: подсказку на старте даст сам агент,
а счётчики `files/tasks.json` у `weekly-report` имеют фолбэк на прямой подсчёт
по `tasks.md`.

Точная граница по Node на клиенте: установка и обновление плагинов его не
требуют ни на macOS/Linux, ни на Windows; на Node остаются хуки Claude Code
(этот раздел) и скрипт `base-sync` — `node .claude/sync-base.cjs`, разовая
сверка с base, а не повседневный путь.

## Как пользоваться этим документом

0. Obsidian поставлен и папка подключена как vault — «Шаг 0» выше.
1. Скиллы уже в vault — режимом из раздела выше (клон базы, plugin marketplace или отдельные скиллы).
2. **Спроси, какой уровень настройки он хочет** (см. ниже), и назови примерное время.
3. Задавай вопросы **по одному**. У большинства настроек есть приемлемый дефолт —
   предлагай его явно, чтобы пользователь мог ответить «да, дефолт» одним словом.

   **Нумеруй каждый вопрос — `1 / 10`, `2 / 10`** и так далее, отдельной строкой перед
   текстом вопроса. Так видно, сколько осталось, и интервью не выглядит бесконечным.
   Прежде чем задать первый, посчитай, сколько вопросов реально будет в выбранном
   уровне (не все применимы к каждому vault), и назови это число вслух. Ориентир:
   обязательный уровень — 2 вопроса, подробный — 13–16. Если по ходу число изменилось —
   скажи новое и нумеруй уже по нему, а не молча сбивай счёт.

   **Спрашивай интерактивным инструментом, если он есть** — `AskUserQuestion` в Claude
   Code, `Clarify` или аналог в другом агенте: пользователь отвечает кликом, а не
   печатает. Правила те же: рекомендуемый вариант **первым** и с пометкой
   «(рекомендуется)», номер `N / M` — в заголовке или первой строке вопроса, пояснение
   и пример — в описании варианта. Свободный ответ («своё название», «другие домены»)
   инструменты дают сами. Если интерактивного инструмента нет — задавай вопрос текстом
   в том же формате.
4. **Голых вопросов не задавай.** Пользователь видит фичу впервые и не обязан знать,
   что стоит за `# Week+` или `➕`. Каждый вопрос — это три вещи:
   1) строка-другая, что фича даёт;
   2) короткий пример (2–5 строк того, как это выглядит в `tasks.md`, в имени файла,
      в списке задач) — если фичу можно показать, показывай, а не описывай;
   3) явная рекомендация: «Рекомендую оставить» / «Рекомендую не включать».
      Рекомендуемый вариант ставь первым — в начале интервью пользователю обещано,
      что при сомнениях можно брать первый.

   ```
   3 / 14
   Оставляем эмодзи-маркеры дат: ➕ когда задача создана, ✅ когда закрыта?
   Так выглядит список задач с ними:

     - [x] Настроить бэкапы ➕ 2026-07-24 ✅ 2026-07-27
     - [ ] Дописать отчёт ➕ 2026-07-30

   По ним считается возраст задачи в list-tasks и попадание в недельный отчёт.
   Рекомендую оставить.
   ```

   Для cross-cutting-настроек примеры уже написаны ниже — бери оттуда. Для остальных
   показывай 2–3 реальные строки из vault пользователя: свой файл понятнее шаблонного.
5. После ответов отредактируй файлы vault пользователя (не этот репозиторий, если ты
   работаешь из отдельного чекаута base).
6. В конце прогони **финальный чек-лист** и покажи короткий диф изменений.

## Уровни настройки (спроси первым делом)

> «Настроить скиллы можно на двух уровнях:
> **обязательный** — ~2–3 минуты, 2 вопроса, минимум чтобы скиллы были связными;
> **подробный** — ~10–15 минут, 13–16 вопросов, тонкая настройка под твою предметную
> область и привычки.
> Можно начать с обязательного и добить подробный позже. Вопросы буду нумеровать
> (`1 / 14`, `2 / 14`), чтобы было видно, сколько осталось.
>
> Если вопрос непонятен — выбирай первый вариант, он рекомендуемый. Ничего необратимого
> в ответах нет: любую настройку потом меняем одной фразой.
>
> Какой уровень делаем?»

Эту оговорку про первый вариант проговори **до первого вопроса** и дальше не повторяй.
Раз она дана — держи слово: **первым в каждом вопросе идёт рекомендуемый вариант**,
и дефолт из описаний ниже. Не начинай вопрос с альтернативы, даже когда она короче.

Принцип: в **обязательной** группе только то, у чего нет универсального дефолта.
Всё остальное — в **подробной**, и у каждого пункта есть приемлемый дефолт.

## Группа 1 — Обязательные (~2–3 мин)

Проходятся всегда, на любом уровне.

### 1.1 Название и тип проекта

Имя проекта — это же имя vault в Obsidian и в deeplink (см. «Шаг 0»). Тип задаёт тон
доменным папкам, категориям sensitivity, направлениям и дню сбора отчёта.

- **Вопрос:** «Как называется проект? Например: `home`, `work`, `CompanyName`.»
- **Дефолт:** имя папки vault — предложи его и дай подтвердить одним словом.
- **Тип:** выведи из имени и назови вслух, а не спрашивай заново: `home` и подобное →
  домашний, `work` / название компании → рабочий. Переспрашивай, только если из имени
  не понять.
- **Что правит:** примеры доменных папок и направлений отчёта формулируй в духе
  выбранного типа (рабочий → проекты/подрядчики/инфраструктура; домашний → быт/финансы/
  здоровье/учёба). Если пользователь дал конкретные домены — используй их. От типа
  зависит и дефолтный день сбора недельного отчёта (см. раздел weekly-report).

### 1.2 Расположение vault и `tasks.md`

- **Вопрос:** «`tasks.md` лежит в корне vault, а рядом `Log/`, `Notes/`, `files/`?
  Если нет — где они?» Покажи ожидаемый расклад:

  ```
  tasks.md                      лестница задач
  Log/2026/07/2026-07-31.md     дневной лог
  Log/Reports/2026-07-31.md     недельный отчёт
  Notes/                        заметки
  files/                        вложения (из поиска Obsidian исключены)
  ```
- **Дефолт:** `tasks.md` в корне vault; `Log/`, `Log/Reports/`, `Notes/`, `files/` рядом.
- **Что правит:** если пути другие — поправь упоминания путей во всех скиллах
  (`tasks.md`, `Log/YYYY/MM/YYYY-MM-DD.md`, `Log/Reports/`, `Notes/`) и в
  `.claude/hooks/tasks-startup.mjs`.

## Группа 2 — Подробные (~10–15 мин)

Включает обязательные. У каждого пункта есть дефолт — предлагай его.

### Cross-cutting (влияет на несколько скиллов)

У каждой настройки ниже готов пример — показывай его в вопросе (см. правило 4 в
«Как пользоваться этим документом»).

#### Маркеры дат — дефолт `➕` / `✅`, рекомендуй оставить

Что даёт: у каждой задачи видно, когда она заведена и когда закрыта. По этим датам
`list-tasks` считает возраст («висит 9 дней»), а `weekly-report` отбирает, что попало
в отчёт за неделю.

```markdown
- [x] Настроить бэкапы ➕ 2026-07-24 ✅ 2026-07-27
- [ ] Дописать отчёт ➕ 2026-07-30
```

Альтернатива — текстовые маркеры (`created: 2026-07-30`, `done: 2026-07-27`): читаемо
в любом редакторе, но плагин Tasks в Obsidian их не подсветит.

Вопрос: «Оставляем эмодзи-маркеры дат `➕`/`✅` или текстовые `created:`/`done:`?»
Что правит: new-task, close-task, list-tasks, weekly-report. `.claude/gen-tasks-json.cjs`
маркеры не парсит (только `- [ ]`/`- [x]`) — его трогать не нужно.

#### Секции `# Week:` / `# Week+` — дефолт «делим», рекомендуй оставить

Что даёт: активные задачи разделены на текущую неделю и более дальний горизонт, при
этом обе секции остаются в одном файле.

```markdown
# Week:
- [x] Починить импорт ➕ 2026-07-27 ✅ 2026-07-29
- [ ] Дописать отчёт ➕ 2026-07-30

# Week+
- [ ] Разобрать архив писем ➕ 2026-07-28
```

Вопрос: «Оставляем разделение активных задач на `# Week:` и `# Week+`?»
Что правит: если не нужно — убери упоминания секций и строки-легенды из new-task,
close-task, list-tasks, weekly-report, obsidian-vault; задачи ведутся одним плоским
списком.

#### Про что не спрашивать

Это устройство ядра, а не настройка. Вопросов не задавай, времени пользователя на них
не трать; меняй, только если он сам попросил.

| Что | Как в ядре |
|---|---|
| Бэклог `tasks-future.md` | есть всегда — часть лестницы `tasks.md` → `tasks-future.md` → `ideas.md` |
| Имена служебных папок | по-английски (`Log/`, `Notes/`, `Log/Reports/`, `files/`); имена заметок и контент — на любом языке |
| Корневой `index.md` | создаётся по умолчанию как точка входа: ссылки на лестницу, `Log/`, `Notes/` и ключевые заметки |
| Структура `Notes/` | вечные ноты в корне `Notes/`, остальное — в `Notes/YYYY/MM/` |
| Лимит корня `Notes/` | 10 вечных нот |
| Автокоммит | нет: `git commit` делает пользователь, когда ему удобно. По явной просьбе — добавь шаг `git commit` в new-task, close-task, worklog |

## Почта для weekly-review

Раздел 8 скилла `weekly-review` разбирает входящие письма в задачи, но не знает, чем ты читаешь почту. Выясни и запиши в vault:

1. **Нужен ли шаг вообще.** Если пользователь не хочет заводить задачи из почты — предложи удалить раздел 8 из скилла целиком, а не оставлять мёртвым.
2. **Адрес или ящик**, входящие которого разбираются.
3. **Чем читать**: установленный скилл для почты, MCP-инструмент провайдера, или ничего. В последнем случае скилл сам пропускает раздел — это штатное поведение, менять его не нужно.

Впиши ответы прямо в раздел 8 скилла `weekly-review`, заменив общую формулировку на конкретную. Плейсхолдеров после адаптации остаться не должно.

## Синхронизация вольта между устройствами (`.stignore`)

Спроси, синхронизирует ли пользователь vault между машинами и чем. Правила в репозитории
написаны под Syncthing: `.stignore` (файл устройства, приезжает клоном, содержит
`#include .stignore-common`) и `.stignore-common` (общие правила, разъезжаются синком).

- **Синка нет или это Git/Dropbox/iCloud** — не трогай файлы и не удаляй их: они не мешают,
  а Syncthing может появиться позже. Скажи об этом одной строкой и иди дальше.
- **Есть Syncthing, вольт = folder** — делать нечего, всё уже на месте. Проверь только, что
  на машинах, куда vault попал не клоном, а синком, лежит свой `.stignore`: Syncthing его не
  разносит, и без него устройство начнёт тянуть чужие `workspace.json`.
- **Есть Syncthing, folder — родительская папка нескольких вольтов** — в её корневом
  `.stignore` добавь `#include <вольт>/.stignore-common` (путь считается от корня folder'а).
  Правила common рассчитаны на обе раскладки, переписывать их не нужно.

Если пользователь сам вёл `.stignore` до адаптации — не затирай: перенеси его строки в
секцию локальных правил под `#include`, а всё, что уже есть в common, выбрось как дубль.
Помни про порядок: первое совпадение выигрывает, поэтому `!`-исключения к правилам из common
должны стоять **выше** строки `#include`.

## Синхронизация после форка (skills-lock.json v2)

Адаптация под пользователя — разовая. Дальше base развивается, и наследник должен уметь подтягивать обновления, не теряя свои кастомизации. Для этого нужны скрипт `.claude/sync-base.cjs` и скилл `base-sync` — в режиме 1 (клон базы) они уже в vault, копировать не нужно; в режиме 3 (только скиллы) добавь их, если пользователь хочет отслеживать обновления base.

1. **Только для режима 1** (vault получен клоном базы через `git clone`): сразу после
   клона разведи remote, чтобы личный vault не уехал в публичную базу:

   ```bash
   git remote rename origin upstream
   git remote set-url --push upstream DISABLED
   git branch --unset-upstream
   ```

   `upstream` остаётся для `git fetch` за обновлениями базы. Свой приватный remote,
   если он нужен, добавляй отдельно под именем `origin`.

   В режиме 3 (только скиллы) этот шаг не выполняй: там `origin` — уже собственный
   приватный remote пользователя, а не публичная база, и его переименование и отключение
   push сломает то, что он сам настроил.
2. Один раз: `node .claude/sync-base.cjs bootstrap` — заводит блок `baseSync` в `skills-lock.json`, сопоставляет локальные имена с base по алиасам (`add-task→new-task`, `list→list-tasks`, `*-vault→obsidian-vault`), помечает уже разошедшиеся скиллы `customized: true`, отсутствующие у наследника — `status: "not-imported"`. Путь к base — в `baseSync.base.path` (дефолт `../../obsidian-agent-base`); поправь, если base лежит иначе.

   Клон base должен физически лежать по этому пути **до** запуска: `bootstrap` не
   скачивает его сам и падает с «Не найден base». И следи за веткой клона — bootstrap
   видит только те скиллы, что есть в base на его текущем коммите; про остальные
   локальные скиллы он теперь предупреждает отдельной строкой, но в lock они не
   попадут, и их правки при обновлении base не отследятся.
3. Дальше по запросу через скилл `base-sync`: `status` (сводка), `diff <skill>`, `stamp <skill>`.

`skills-lock.json` v2 совместим с v1: блок внешних github-скиллов (`skills`) не трогается. Хэш скилла считается без `name:`/`description:` — эти строки у наследников легитимно разные. Кастомизации (путь лога, секции `# Week:`, переименованный vault-скилл) при `BASE-CHANGED`/`BOTH-CHANGED` сохраняются вручную через скилл, скрипт сам `SKILL.md` не правит.

## Финал: убрать демо

В режиме 1 последним шагом выполни скилл `demo-content-delete`. Он сверяет демо-файлы (примеры логов, отчёта и заметок) с хэшами из `demo-manifest.json`, показывает дифф по тем, что пользователь успел поправить, и удаляет себя.

Двумя отдельными вопросами он предложит убрать ещё две группы: инструкции по развёртыванию (`README.md`, `README_ru.md`, этот файл, `CONTRIBUTING.md`) и файлы, нужные только разработке базы (`tests/`, `.github/`, `.githooks/`, `cliff.toml`).

**Файлы лестницы он не трогает.** Задачи в `tasks.md`, `tasks-future.md` и остальных — не демо: это онбординг, который проходит каждый пользователь (прочитать README, перечислить, где ещё лежат задачи, перенести их сюда, записать первый день, собрать отчёт). Пользователь закрывает их обычным `close-task`, а не удаляет.

> Демо-файл: скилл `demo-content-delete` предложит удалить этот файл.
