# task-prepare

Берёшь **одну** задачу и поднимаешь по ней контекст: что уже известно, как устроено сейчас, что мешает, что делать. Работа read-only - смотришь, а не меняешь.

Скилл рассчитан на запуск без человека (`claude -p`), где ответ в чат никто не прочитает. Поэтому результат обязан лечь в файлы. Если разбор остался только в переписке - работа не сделана.

Конвенции вольта (куда класть заметки, как писать wikilinks, что считать открытым чекбоксом) - в `obsidian-vault`.

## Какую задачу берём

- **Аргумент `all`** - пакетный режим, см. раздел «Режим all» в конце. Всё, что ниже, описывает разбор одной задачи; в режиме `all` этим занимается каждый субагент по отдельности.
- **Аргумент - число** (`/task-prepare 3`) - это порядковый номер открытой задачи в `tasks.md`, нумерация как в `task-prepare status`. Не разгадывай сам, спроси CLI: `task-prepare run 3 --dry-run` напечатает, какая это задача. Дальше работай с ней как с обычным аргументом.
- **Есть аргумент** - работаешь ровно с ней. Найди её строку в `tasks.md`; если строки нет, работай с текстом аргумента и не выдумывай, что он из `tasks.md`.
- **Аргумента нет** - первая открытая задача в порядке файла `tasks.md`. Закрытой считается только `- [x]`; пустой чекбокс, статус стороннего плагина и незачёркнутый буллет - открытые. Не прыгай в `# Week+`, пока выше есть открытая.
- **Открытых задач нет** - скажи прямо и закончи. Не выдумывай работу.

Ровно одна задача за запуск. Заманчиво «раз уж я тут» подготовить соседнюю - не надо: CLI ведёт учёт по одной задаче за вызов, и лишние заметки останутся без отметки.

## Шаг 0. Проверить, не подготовлена ли уже

**Всегда первым действием**, до любого исследования:

```bash
./.scripts/task-prepare check "<строка задачи как есть, с эмодзи>"
```

- **exit 0** - задача уже подготовлена, в stdout путь к заметке. Прочитай заметку, назови её пользователю и **закончи**. Ничего не исследуй заново.
- **exit 1** - не подготовлена. Но прежде чем исследовать, посмотри подпункты самой задачи: если там уже есть `- Контекст собран: [[...]]` и заметка существует, значит разбор делали на другой машине - состояние CLI лежит в `.claude/`, а он обычно в `.gitignore`. Тогда не разбирай заново: позови `mark` с путём к существующей заметке и закончи как в ветке exit 0.
- Ни того, ни другого - работай дальше.

Переделывать разбор заново - только если пользователь явно попросил («переделай», «собери заново») или запуск был с `--force`. Само по себе «заметка выглядит неполной» основанием не является: допиши недостающее в существующую заметку, а не создавай вторую.

Если `./.scripts/task-prepare` в вольте нет - скилл работает и без него, просто пропусти шаги 0 и артефакт 3, и скажи об этом в ответе.

## Шаг 1. Сразу завести пустую заметку

Как только `check` сказал «не подготовлена» - **до** всякого исследования создай файл заметки по пути из артефакта 1 и запиши в него одну строку с датой и временем начала:

```bash
date '+%Y-%m-%d %H:%M'
```

```md
Разбор задачи "<текст задачи>" (➕ <дата постановки>). Исследование read-only, начато 2026-08-17 16:15.
```

Время бери командой, а не из головы: своё локальное время ты не знаешь, а расхождение в разбор попадёт навсегда.

Смысл в том, что исследование идёт минутами, а в headless-режиме снаружи не видно ничего. Пустая заметка с отметкой времени - единственный признак, что работа началась и когда именно. Заполняется она по ходу; если прогон оборвётся, останется хотя бы след с временем старта, а не пустота.

## Границы: только чтение

Пока идёт исследование, нельзя:

- редактировать заметки, код, таблицы, документы, дневные логи;
- отправлять сообщения, письма, формы, комментарии, заявки;
- менять настройки, доступы, статусы, карточки во внешних системах, трекерах, админках;
- запускать команды, меняющие внешнее состояние, ставить зависимости;
- закрывать задачу или писать в дневной лог.

Можно: читать файлы, искать по вольту, открывать сайты и внутренние страницы, делать скриншоты и DOM-снимки, читать документацию, дёргать read-only API и отчёты.

Три исключения - собственные артефакты скилла из раздела ниже: заметка-разбор, подпункт-ссылка в задаче, отметка в CLI.

Четвёртое исключение - **разовый скрипт для замера**. «Только чтение» относится к данным, а не к своим инструментам: если для цифр нужен скрипт, заведи его как обычный файл в том проекте, которому он принадлежит, и запусти. Запрет на изменения не означает, что скрипт надо ужимать в инлайновую однострочку - именно так появляются висяки и повторно наступают на уже описанные грабли.

## Исследование

1. **Локальный контекст.** Подпункты задачи в `tasks.md`, соседние задачи той же темы, упоминания в `Log/`, `projects.md`, связанные заметки по wikilinks. Если у вольта есть база знаний и задача про рабочий процесс - как что-то устроено, кто что нажимает, что должно происходить дальше - спрашивай её через профильный скилл вольта (например `knowledge-base`), а не грепом наугад: там регламенты и расшифровки видеоинструкций, где процесс описан словами самих сотрудников.
2. **Историю.** Задача с давним `➕` обычно уже разбиралась - поищи прошлые заметки и логи по ключевым словам, прежде чем разбирать с нуля.
3. **Внешний контекст через браузер**, если он доступен: трекер, админка, дашборд, ссылка из самой задачи, документация сервиса. Браузер полезен, даже когда часть ответа есть в файлах, - он показывает, как оно выглядит сейчас, а не как записано.
4. **Данные, а не впечатления.** Если по задаче можно посчитать масштаб (сколько объектов затронуто, как часто случается, сколько времени тратится) - посчитай через read-only API или выгрузку и приложи цифры. Разбор без масштаба заставляет человека считать самому.

### Как ходить во внешние API

Два правила, оба из реального висяка на 13 минут.

**Иди через клиент проекта, а не инлайном.** Если для системы есть готовый клиент со своим скиллом (`crm-api-client` и подобные) - работай через него и заведи скрипт рядом с остальными его примерами. В таком скилле уже описаны грабли этого API, а инлайновый `python3 -c` или `curl` начинает с нуля и наступает на них заново. Прямые запросы к API мимо клиента - только если клиента нет.

**Ставь таймаут на каждый сетевой вызов.** `urlopen(req)`, `requests.get()`, `fetch` без таймаута ждут вечно, а обработчик ошибок ловит HTTP-коды, но не зависшее соединение. В headless-запуске это смертельно: вывода не видно, процесс жив, снаружи висяк неотличим от долгой работы. Таймаут на запрос, потолок на число страниц, и печатай прогресс по ходу, а не одним куском в конце - иначе `.output` фоновой задачи остаётся пустым и понять, где остановилось, нельзя.

Если браузер применить невозможно - объясни одной строкой почему и продолжай по файлам. Отсутствие браузера не повод не делать разбор.

Крупная задача, план по которой не сводится к нескольким шагам - прогони через `decompose` и вложи результат в заметку.

## Обязательные артефакты

Запуск считается выполненным, когда есть **все три**. Не два.

Единственное исключение - субагент в режиме `all`: он делает первый и третий, а второй за всех делает оркестратор. Если тебя запустили как субагента для одной задачи из пакета, `tasks.md` не трогай.

**1. Заметка-разбор.** Путь по конвенции вольта: `Notes/YYYY/MM/<Короткое название> - разбор.md`, где `YYYY/MM` - текущий месяц. Если у темы уже есть папка мини-проекта - клади туда. Название - по сути задачи, а не по её первой строке целиком.

**2. Подпункт-ссылка в `tasks.md`.** С отступом табом, **последним** из подпунктов задачи. У задачи обычно уже есть свои подпункты - вставляй после них, а не сразу под строкой задачи, иначе ссылка окажется посреди чужого текста:

```md
- [ ] <задача как была> ➕ 2026-08-15
	- <её собственный подпункт, был раньше>
	- <и второй, тоже был>
	- Контекст собран: [[<Короткое название> - разбор]].
```

Саму строку задачи не трогай: ни текст, ни чекбокс, ни эмодзи, ни позицию в файле. Если подпункт со ссылкой на этот разбор уже есть - не дублируй.

**3. Отметка в CLI.** Последним действием, уже после того как заметка записана:

```bash
./.scripts/task-prepare mark "<строка задачи как есть>" "Notes/2026/08/<Короткое название> - разбор.md"
```

Ключ идемпотентности считает сам CLI. Не пиши в `.claude/task-prepare-state.json` руками и не выводи ключ сам - иначе повторный запуск не найдёт задачу и пойдёт разбирать её заново.

## Шаблон заметки

Заголовка H1 не надо - имя файла и есть заголовок. Первая строка задаёт рамку, дальше тематические разделы.

```md
Разбор задачи "<текст задачи>" (➕ <дата постановки>). Исследование read-only, начато <дата время>, изменений не делалось.

Короткий вывод: <2-3 строки - что выяснилось и что с этим делать. Пишется последним,
когда разбор готов. Человек читает эти строки и решает, нужно ли ему остальное.>

## Как устроено сейчас

<Что удалось выяснить: как работает система, кто участвует, где живут данные.
Конкретика со ссылками на объекты, файлы, страницы, номера задач и сценариев.>

## <Тематический раздел по сути задачи>

<Разбор, варианты, цифры, таблицы. Разделов столько, сколько нужно теме.>

## Что делать

<Минимальный план шагами. Для каждого шага - кто может его сделать
и что в нём необратимо.>

## Открытые вопросы

- <Вопрос, на который нужен ответ человека, одной строкой - чтобы отвечался «да/нет» или «А, не Б».>

## Смежное

- <Связанные задачи и заметки через [[wikilink]], одной строкой каждая: чем связаны.>
```

Короткий вывод и разделы «Как устроено сейчас», «Что делать», «Открытые вопросы» обязательны. Пустых вопросов не бывает: если вопросов правда нет, напиши «Блокеров не осталось» и что именно это разблокирует.

## Ответ в чат

Коротко, без пересказа заметки - её и так можно открыть:

```md
Подготовил: <текст задачи>

Разбор: [[<Короткое название> - разбор]]

Главное:
- <вывод, меняющий решение>
- <вывод, меняющий решение>

Нужно от тебя:
- <вопрос или «ничего, можно делать»>
```

Дальше **остановись**. Само выполнение задачи - отдельный шаг, после «ок» от человека. В headless-запуске никакого «ок» не будет, значит выполнение не начинается никогда.

## Проверка перед завершением

1. Обработана ровно одна задача.
2. `check` был вызван **до** исследования, а не после.
2а. Заметка заведена сразу после `check`, время старта в ней взято командой `date`, а не придумано.
3. Заметка записана, в ней есть «Как устроено сейчас», «Что делать», «Открытые вопросы».
4. Подпункт-ссылка стоит под задачей, сама строка задачи не изменена.
5. `task-prepare mark` вызван и вернул успех.
6. Ничего не изменено во внешних системах, задача не закрыта, в дневной лог не писалось.
7. В ответе сказано, использовался ли браузер, а если нет - почему.

Дальше движение по задаче фиксируется через `worklog`, закрытие - через `close-task`.

## Режим all

`/task-prepare all` разбирает **все** ещё не подготовленные задачи, раздавая независимые по субагентам. Ты в этом режиме оркестратор: сам не исследуешь, а собираешь список, делишь его и сводишь результаты.

### 1. Собрать список и показать масштаб

```bash
task-prepare pending
```

Отдаёт сырые строки задач, которые открыты и ещё не разбирались, по одной на строку. Именно эти строки передавай дальше без изменений - по ним считается ключ идемпотентности.

Скажи пользователю, сколько задач нашлось, до того как запускать работу. Сорок задач - это сорок исследований; человек имеет право узнать объём заранее. Если он назвал число (`/task-prepare all 5`) - возьми столько первых: `task-prepare pending 5`.

### 2. Разделить на независимые и связанные

Две задачи **связаны**, если разбор одной меняет выводы другой: они про один объект, сценарий, отчёт или систему; одна явно блокирует другую; вторая - следствие первой. Признаки видны по тексту задач и их подпунктам, лезть в файлы ради этого не надо.

- **Независимые** - по одному субагенту на задачу, запускаются параллельно.
- **Связанные** - в одну цепочку, один субагент на всю цепочку, задачи внутри разбираются по очереди. Так второй разбор видит выводы первого, а не повторяет его работу.

Запускай пачками, не больше **4-5 субагентов за раз**. Дождался пачку - собрал результаты - запустил следующую. Иначе исследования начнут упираться в лимиты внешних систем, а отчёт станет нечитаемым.

### 3. Что делает субагент, а что ты

Это разделение обязательно, иначе параллельные субагенты подерутся за `tasks.md`.

**Кого запускать.** Обычного субагента общего назначения, который выполнит **этот** скилл для одной задачи. Не агента `task-do`: он двухрежимный, начинает с собственного выбора задачи, а главное - в режиме подготовки пишет подпункт в `tasks.md` сам. В пачке из четырёх это ровно та гонка, которую разделение ниже и предотвращает.

**Субагент** получает текст задачи и выполняет этот скилл для неё, но артефактов у него **два, а не три**:

1. заметка-разбор;
2. `task-prepare mark` - безопасно, состояние правится под блокировкой;
3. ~~подпункт в `tasks.md`~~ - **не трогает**.

Возвращает: текст задачи, путь к заметке, 2-3 главных вывода, открытые вопросы.

В задании субагенту напиши прямо: «это задача из пакета, `tasks.md` не трогай» и «не останавливайся на паузу, доведи оба артефакта до конца». Без второй фразы субагент склонен отчитаться на середине - с заметкой-рамкой и без `mark`, и тогда задача останется неотмеченной, а следующий прогон разберёт её заново.

**Ты** после каждой пачки дописываешь подпункты `- Контекст собран: [[...]]` в `tasks.md` - последовательно, сам, за всех субагентов сразу. Файл один, писать в него параллельно нельзя.

### 4. Свести результат

```md
Разобрано задач: <N> из <всего pending>

- <задача> → [[<заметка>]]
  <главный вывод одной строкой>

Нужно от тебя (одним пакетом):
- <вопрос> (по задаче <какой>)
```

Открытые вопросы из всех разборов собери в один список: человек ответит пакетом, а не будет открывать сорок заметок.
